# 旧形式からの移し替え

## 扱うこと

旧形式の判断ファイルや SKILL.md を今の型に移すとき、型に無い項目をどこへ移すか

## 答え方と理由

### 0. 判断全体

実装の判断。旧形式は、「求める材料・答え・値・計算・道具・理由・却下した案・当てはまる範囲と限界」の章を持つ判断ファイルと、役割・聞かれ方・依存の順・判断ファイルの形・未決の章か、要件と手順の章を持つ SKILL.md を指す。手順の写しをどう見つけるかは、この判断では答えない（→ [手順の写し](impl-procedure-copies.md)）。

- （根拠）設計文書は今の型を定めるが、旧形式の項目をどこへ移すかは書いていない。2026-10-27〜28 に13スキルを移したときの移し方を、人が確かめて残す。（決定日：2026-10-29）

### 1. 「却下した案」は、答え方の「〜しない」と、その理由へ移す

「却下した案」の表の行は、その案に当たる答え方の中に「〜しない」と名指しで書き、表の「理由」を、その答え方の理由に移す。表の理由が「理由N」を指すだけなら、その理由をその答え方の下に置く。案の理由を落とさない。

1. （原因）移し替えのあとで見直すと、却下した案の理由を1つ落としていた。（発生日：2026-10-28）

### 2. 「当てはまる範囲と限界」は、中身で移し先を分ける

| 中身 | 移し先 |
|---|---|
| 判断が成り立つ前提（〜で確かめた、〜のときに限る） | 「0. 判断全体」の前提（「〜のときに、次のとおりにする」） |
| この判断が答えない問い・ほかの判断への案内 | 「0. 判断全体」の答えない問い（`〜は、この判断では答えない（→ その判断）`） |
| 分かっている限界（旅行を検知できない、など） | 当てはまる答え方の文 |
| まだ決めていないこと・確かめていないこと | 「未決」。暫定の扱いを添え、本文の当てはまる所から ID で指す |
| 直すきっかけ（仕様が変わったら見直す、など） | 書かない |
| 移した経緯（いつどこから移した、など） | 書かない。git の履歴が持つ |
| 「理由が記録されていない（未決）」 | 未決にせず、その答え方の理由を「記録なし」にする |

1. （原因）分かっている限界を未決に置いたら、見直しで「決まっていない事ではない」と分かった。（発生日：2026-10-28）

### 3. SKILL.md の未決は、該当する判断ファイルの未決へ移す

SKILL.md の「未決」の章の項目は、該当する判断ファイルの「未決」に移し、SKILL.md から消す。理由の記録が無いことだけを書いた項目は、未決にせず、判断ファイルの理由を「記録なし」にする。SKILL.md の役割・聞かれ方・依存の順・判断ファイルの形の章は、定型文と索引の「依存する判断」が持つので、消す。

1. 記録なし

### 4. スキルの分け方が決まっていない判断は、判断ファイルの未決に書く

「generic-logic へ移す候補」のように、どのスキルに置くかが決まっていない判断は、その判断ファイルの「未決」に書き、暫定の扱いを「このスキルに置いたまま答える」にする。本文から ID で指さない。

1. （根拠）答え方そのものは決まっているので、本文から指すと、決まっている答えまで「未決」として返る。（決定日：2026-10-29）

### 5. 旧形式の手順は、文ごとに写しでないかを確かめてから移す

旧形式の手順を、中身を保ったまま新しい章へ移さない。文ごとに、表の行の写し・判断の答えの写し・目的や要求や定型文の繰り返し・設計の説明でないかを確かめ、当たる文は、表の行をIDで指す1文にするか、消す。依頼先や判断先の名前をIDに置き換えるだけで済ませない。

1. （原因）コンディションの評価アプリの旧形式の手順を移したとき、中身を保ったまま新しい章に入れ、依頼先の名前を `R1` などに置き換えただけだったので、依頼の例の表と、判断の答えの写しが残った。型の計算はすべて通り、指示者に指摘されるまで気づかなかった。（発生日：2026-11-19）

### 6. 旧形式の要件は、項目ごとに要求・判断・打ち手のどれかへ分けて移す

旧形式の要件と手順の章を、要求と打ち手の章へ移すときは、要件の項目ごとに次の表で移し先を決める。要件の文を、そのまま要求の見出しにしない。

| 要件の項目の中身 | 移し先 |
|---|---|
| 指示者が結果に求めること（兆候に気付く・記録がそろう、など） | 要求の `##` の見出し。[アプリケーションスキルの型](app-skill-shape.md) の【要求の文末】の形に書き直す |
| 方法（何で示すか・何を添えるか・どう数えるか、など） | 判断ファイル。同じ答え方がもうあれば移さずに消し、無ければ、まだ切り出していない判断の判断ファイルに答え方として足す |
| 守りたいもの（手元の変更を壊さない、など） | 要求に「〜を失いたくない」「〜を減らしたい」の形で書く |
| 避け方（push しない・解釈を書かない、など） | それを守る判断の答え方の「〜しない」。守る判断が無ければ、まだ切り出していない判断の判断ファイルに足す |
| 実行する順番（同期してから評価する、など） | 打ち手の中の手順 |
| 何を守るための制約か、指示者にも分からないもの | 移さず、残すかを指示者に聞く |

手順の節は、見出しが指していた要件の要求の下へ、`###` の打ち手として移す。いくつかの要件を指していた節は、それを最初に必要とする要求の下に置き、どの要件も指していなかった記録と報告の節は、最後の `##` にする。

1. （原因）コンディションの評価アプリの要件を整理したとき、要件の文を短くしただけの案を出したら、「警戒線で示す」「目標との距離と方向で示す」などの方法が残り、指示者が、方法は判断だと指摘した。どれも判断ファイルにすでにあった。（発生日：2026-11-20）
2. （原因）同じアプリの要件の制約5つ（医学的な判断をしない・書き込み先・外向きのアクションなど）は、何の判断のためのものだったかの背景を、指示者も失っていて、指示者が削除した。（発生日：2026-11-20）

# 文脈と種類の見分け方

## 扱うこと

判断をスキルへ振り分けるとき・スキルを分ける・まとめるとき、文脈を何で切り、core-logic と generic-logic を何で見分けるか

## 答え方と理由

### 0. 判断全体

実装の判断。ロジックスキルとアプリケーションスキルのどちらにするかと、core-logic と generic-logic の定義は、この判断では答えない（→ [スキルの種類](skill-kinds.md)）。

- （根拠）設計文書の 1-2・2-1 は、文脈を1つに区切ることと、人によって答えが分かれるかで種類を分けることを決めているが、文脈を何で切るかと、答え方と理由のどちらを見て分けるかは書いていない。（決定日：2026-11-20）

### 1. 文脈は、扱うことの問いで切り、理由に出てくる環境で切らない

文脈は、判断の扱うことが「誰が、どんな作業をするときの問いか」で切る。理由や答え方の条件に出てくる環境（OS・シェル・ツールの名前）で切らない。環境ごとの違いは、同じ判断ファイルの答え方の条件（「Windowsの Git Bash では、」など）と理由に置く。答え方の中身が、その環境の仕様と癖そのものなら、この答え方ではなく答え方4に従う。

1. （原因）Windows の操作の中核判断を分けるとき、Windows のシェルと Claude Code の2つの文脈で切った。どちらの判断も問いは「AIエージェントをどう動かすか」で、Windows や Claude Code の事情は理由に出てくるだけだった。指示者に指摘されて、AIエージェントの動かし方の1つの中核判断にまとめ直した。（発生日：2026-11-20）

### 2. 種類は、答え方が人によって分かれるかで見て、理由の種類で見ない

core-logic と generic-logic は、答え方（どうするか）が人によって分かれるかで見分ける。理由が知見だからといって generic-logic にしない。答え方に作成者の選択（使う道具・前提にする地域・値の持ち方など）が入っていれば core-logic にし、事実は理由に知見として置く。答え方が事実だけで決まり、誰がやっても同じになるときだけ generic-logic にする。

1. （原因）「スキルのPythonスクリプトは `uv run` で起動する」と「JSTを `+09:00` の固定オフセットで持つ」を、理由が知見なので一般的な業務知識に分けた。実際は、依存を uv で固定することも、時刻をJSTで持つことも作成者の選択で、中核判断へ移し直した。（発生日：2026-11-20）

### 3. 選択が答え方に書かれていなければ、答え方を足して見えるようにする

作成者の選択が、判断全体の条件（「スクリプトが uv で依存を固定しているときに」など）に隠れているときは、その選択を答え方として書き出し、種類を見分けられるようにする。

1. 答え方2の理由1と同じ。

### 4. 公開された環境の仕様と癖を答える一般的な業務知識は、環境（サービス）ごとに分ける

一般的な業務知識のうち、答え方の中身が、ある公開された環境（サービスのサイト・Web API・ファイルの形式など）の仕様と癖そのものであるものは、その環境（提供元のサービス）ごとに1つのスキルに分ける。作業の問いが同じに見えても（「明細をどう取り、どう読むか」など）、別々の環境の知識を1つのスキルにまとめ、環境の違いを判断ファイルの分け方で持たせない。環境に依らない一般的な業務知識（ブラウザの操作・Notion の扱い方など）は、その道具を文脈にする。

1. （原因）金融サービスの5つのサイト（銀行・カード2社・電子マネー・通販）の知識を、作業の問いが同じだとして答え方1を当てはめ、1つの一般的な業務知識にまとめ、サイトごとに判断ファイルを分けた。答え方はどれもそのサイトの仕様と癖そのもので、作成者に理由を問われ、取得元ごとの5つに分け直した。作成者のほかの一般的な業務知識は、サービスごとに分かれていた。（発生日：2026-11-26）
2. （根拠）作成者が、取得元ごとに分けると決めた。一般的な業務知識は、踏んだ落とし穴を足して育て、そのまま渡す。環境の仕様は環境ごとに別々に変わるので、環境ごとにバージョンを上げられ、1つの環境だけを使う導入先にもそのまま渡せる。（決定日：2026-11-26）

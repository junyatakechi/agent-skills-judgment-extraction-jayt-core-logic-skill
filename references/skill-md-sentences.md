# SKILL.md に入れる文

## 扱うこと

SKILL.md に文を足すとき、入れるか、どの定型文を写し、frontmatter に何を書くか

## 答え方と理由

### 0. 判断全体

設計文書を写す判断。

- （知見）設計文書の 3-5 を写した。（出典：人の判断を切り出すAIスキルの設計_v2.2.3 の3-5@2026-11-16）

### 1. 文を消したら実行するAIエージェントの行動が変わるかで、入れるかを決める

| 種類 | 例 | 置き場 |
|---|---|---|
| 設計の説明 | 判断先を差し替えれば、別の人の視点で実行できる | 設計文書だけ |
| スキルを直すときの決まり | 判断先の版が範囲を超えたら、手順と材料を合わせてから範囲を更新する | 設計文書だけ |
| 実行時に効く決まり | 「判断が無い」と返されたら、一般論で埋めず、チャットで指示者に伝える | SKILL.md の最後の章「このスキルの設計上の決まりごと」 |

1. （原因）SKILL.md に設計の説明とスキルを直すときの決まりを書いたら、実行のたびに読まれるのに、実行中の行動は変えなかった。本文は、アプリケーションスキルで約2割、ロジックスキルで約4割がこうした文だった。（発生日：記録なし）

### 2. frontmatter に、従う設計文書を書く

`metadata.design` に設計文書の題名を版つきで、`metadata.design-url` にその場所を書く。YAMLのコメントでは書かない。作る・直すときに何に従わせるかは、frontmatter に書かない（→ 答え方5）。

1. （根拠）YAMLを読み込んで書き戻す道具では、コメントが消えることがある。frontmatter は、スキルを呼んだときには読まれず、スキルを直すためにファイルを開けば読まれ、スキルを渡しても参照先がついて行く。（決定日：記録なし）

### 3. 実行時に効く決まりは、種類ごとの定型文を写し、書き足さない

最後の章「このスキルの設計上の決まりごと」には、種類ごとの定型文だけを置き、書き足さない。手順や表の下で、定型文と同じことを繰り返さない。定型文は、依存するメタ的なスキルに移さず、各スキルに写す。ロジックスキルの定型文の6は、一般的な業務知識（generic-logic）だけが写す。「（一般的な業務知識だけ）」の添え書きは写さない。

アプリケーションスキルの定型文：

```markdown
1. 手順のIDは、表の行を指す。`J` は判断を聞き、`G` はスキルを参照し、`R` は依頼先に頼み、`C` はファイルに従う。中核判断の委任表の判断は、自分の一般論で代えない。それ以外は、目的と要件を満たすように、一般知識も使って考えてよい。
2. 判断を聞くとは、判断先の判断ファイルを読み、判断先のスキルの定型文どおりに材料を集めて計算を流し、聞きたい事の範囲で答え方を当てはめ、欲しい答えの形にそろえることをいう。計算をこのスキルで代わりにしない。まだ切り出していない判断も、このスキルの `references/` の判断ファイルを同じやり方で当てはめる。
3. 答えと理由を組にして使う。必須の材料が無ければ当てはめず、足りないものを結果に書く。
4. 中核判断で「判断が無い」「未決」に当たったら、一般論で埋めず、チャットで指示者に伝える。まだ切り出していない判断で当たったら、一般論で補ってよく、補ったことをチャットで1行伝える。
5. スキルを参照するときは、その作業に入る前に読み込み、作業に当たる判断ファイルに従う。道具は、このスキルが自分で呼ぶ。
6. 依頼先はスキルとして実行させ、そのスクリプトを直接は呼ばない。報告が欲しい結果を満たすかを確かめる。
7. 出力の前に、要件をすべて満たしたかを確かめる。手順の答えだけで足りなければ、目的と要件に沿って補う。中核判断の答えと食い違うことは書かない。
```

ロジックスキルの定型文：

```markdown
1. このスキルは判断を答えるだけで、判断の対象もデータも持たない。対象の値は、材料の写しとして受け取る。データを取りに行かず、保存もせず、IDも受け取らない。
2. 答える範囲は、聞きたい事を索引の「扱うこと」と照らして決める。索引の「依存する判断」にある判断を、先に出す。
3. 判断ファイルの「求める材料」がそろわなければ答えない。計算がある判断は、`uv run <skill-dir>/scripts/judge.py <判断> <材料.json>` で計算する。<判断> は `references/` のファイル名。依存する判断の材料も、一緒に渡す。
4. 答えは、指定された形にそろえ、理由と組にして返す。
5. 中核判断は、判断ファイルで答えられなければ、一般論で答えず「判断が無い」と返す。「未決」に当たったら、未決であることと、決めるまでの暫定の扱いを含める。一般的な業務知識は、判断ファイルに無いことを一般知識で補ってよい。
6. 読み込まれたら、索引の「扱うこと」に当たる作業で、その判断ファイルに従う。どの道具をどう呼ぶかは、判断ファイルの「道具」が示す。手続きは代わりに行わず、呼び出し側が道具を呼ぶ。操作する対象のIDは、材料ではなく、道具の引数で渡す。
```

1. （根拠）定型文はスキルの文脈に依らず、設計だけから決まるので、どのスキルでも同じ文になる。同じ決まりが2か所に分かれると、片方だけが直される。（決定日：記録なし）
2. （根拠）メタ的なスキルに移しても、実行時には依存先を読むので、読む量は減らない。会話が要約されたあとに付け直すスキルは、最近呼んだものから順に枠が埋まるので、最初に読む依存先から落ちる。（決定日：記録なし）

### 4. 本文は【本文の上限】以内にし、収まらなければ外へ分ける

本文は【本文の上限】以内にする。手順は、アプリケーションスキルの SKILL.md の中だけに書く。手順が収まらないときは、手順の一部を別のアプリケーションスキルに分け、外部手順の依頼表で頼む。ロジックスキルの本文が収まらないときは、道具の詳しい部分を道具のコードの docstring に移す。

1. （知見）会話が要約されると、スキルは先頭の5,000トークンだけが付け直され、超えた分は末尾から消える。定型文の章は最後にあるので、超えると最初に消える。（出典：なし）

### 5. 作る・直すときに従わせる先は、導入先のファイルに書く

作る・直すときに何に従わせるかは、frontmatter に書かず、導入先の常に読まれる指示のファイル（`AGENTS.md` など）に書く。

1. （根拠）設計文書をどう実装するかは人・AIエージェント次第で、従わせる先が導入先ごとに違う。（決定日：2026-10-29）

# 依存の宣言と版

## 扱うこと

依存するスキルを書くとき・判断ファイルを変えたとき、版の範囲と版をどう上げるか

## 答え方と理由

### 0. 判断全体

設計文書を写す判断。

- （知見）設計文書の 5-4 の版の規則と 5-8 を写した。（出典：人の判断を切り出すAIスキルの設計_v1.0.0 の5-4・5-8@2026-10-29）

### 1. 依存は、frontmatter の `metadata.dependencies` に書く

アプリケーションスキルは、委任表・参照表・依頼表に出てくるスキルを、すべて `metadata.dependencies` に書く。本文には置かない。ロジックスキルは依存の宣言を持たない。

```yaml
metadata:
  dependencies: >-
    github:junyatakechi/diet-process-<作成者>-core-logic-skill@^0.2.0,
    github:junyatakechi/oura-collection-app-skill@^0.2.0
```

| 項目 | 書き方 |
|---|---|
| 1件の形 | `github:<owner>/<repo>@<版の範囲>` |
| 複数のとき | `,` で区切って1つの文字列に並べる。YAMLのリストは使わない。長くなるときは `>-` で複数行に分けてよい |
| 版の範囲 | npm の書き方で、`^` を使う（`^0.2.0` は 0.3.0 未満、`^1.2.0` は 2.0.0 未満） |

1. （原因）使用するリポジトリ表を SKILL.md の本文に置いたら、実行のたびには使わない表が、スキルを呼ぶたびに読み込まれていた。（発生日：記録なし）
2. （知見）`metadata` の値は文字列だけ。（出典：なし）

### 2. 判断ファイルを変えたら、ロジックスキルの版を上げる

判断ファイルを変えたら、ロジックスキルの版を上げる。版が依存の宣言の範囲を超えたときは、それを参照するアプリケーションスキルの手順や材料を合わせてから、範囲を更新する。範囲の中で上がったときは、アプリケーションスキルを直さない。

1. （根拠）依存の向きがアプリケーションスキルからロジックスキルへの一方向なので、直すのは依存する側。範囲の中の版は、呼び出し側が何も合わせなくてよい変更だけで上がる。（決定日：記録なし）

### 3. 差し替えるときは、宣言の1件も差し替える

判断先や依頼先を別の人のスキルに差し替えるときは、宣言の1件も差し替える。core-logic は作成者で名前が変わるので、委任表の見出しのスキル名も書き替える。版の範囲は、スキルごとに1つ持つ。

1. 記録なし
